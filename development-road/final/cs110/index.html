Plan + huddle

Decisions: I chose a first-person, physics-puzzle exploration game in Unity (C#) inspired by Half-Life style play, because it is a small, testable scope for one developer. I chose to build in this order: core player and puzzle, then modular architecture, tests, save, settings and accessibility. The order follows the dependencies in my contract: tests need a modular design, and settings need the save system. I chose JSON files for saves and settings because they are easy to validate and test. Each stage gets its own test so I know it works before the next one starts. I work solo with no support team, so all decisions and tasks are mine.

Goal: A working scene where the player can walk in first person, pick up and throw a physics prop, press a button to open a door, and save and reload that puzzle state.

My contribution: In my role as the only developer, I will write all the code, set up the Unity project and Git repo (ProjectLevo), make the documentation, and run the tests. I understand the pipeline as: Goal (working project) → Inputs (code and assets) → Build (core interaction, then modules, tests, save, settings, accessibility) → Test (expected behavior at each stage) → Deliver (source, README, run guide and evidence). I will use AI (Gemini and Claude) for help, but I will run and check all code myself to make sure it works, and I will explain my own contribution in my own words.

Open questions: Risks: 53 hours is tight for six stages, so I may cut the puzzle to one button and one door if time runs short. Physics props and movement can feel wrong or glitch (clipping, objects falling through the floor), so I will playtest often. Open questions: which assets I can use and credit, and how much of the "Source-style" movement I should build. What I will test: the room is solvable with 0 console errors, saved state restores after closing and reopening, an invalid save file is handled, settings persist, and the game can be played with the keyboard only.

Selected requirements + actual evidence

Working project foundation

Required evidence: Working source and build (60); authored program logic (35); meaningful tests (20); run guide and evidence map (20); individual explanation (15).

Actual result: In Unity 6.6 (HDRP), TestRoom runs with a first-person player (WASD, mouse look, jump, Source-style acceleration and friction). I can pick up a physics cube with E, throw it with left click, and drop it. A pressure plate opens a sliding door while the cube rests on it and closes it when removed. The scripts are in Assets/Levo/Scripts (Player, Interaction, Puzzle).

Test: 1. WASD + mouse -> walk and look at head height -> observed: walks and looks correctly after I fixed two defects (a leftover Free Camera script was flying the camera, and movement froze because tiny moves were ignored). 2. E on cube within 3.5 m, then left click -> pick up, then throw -> observed: works. 3. Cube on plate, then removed -> door opens, then closes -> observed: works. 4. Cube trapped under the closing door -> no crash -> observed: 0 console errors; the door clips into the cube (known issue).

Evidence location: Docs/stage1_test.png, Assets/Levo/Scripts/, repo github.com/Lexicon-Lexxie/ProjectLevo, commit: https://github.com/Lexicon-Lexxie/ProjectLevo/commit/88a52dfcf7618016ab4870ace9302a6ce50e2dc6

Marked complete: Yes

★ Accessible controls and interface

Required evidence: Demonstrate keyboard access, readable contrast, clear feedback and one user-tested accessibility improvement.

Actual result: The code is split into Core (IPlayerInput), Player (PlayerInputReader, PlayerMovement, PlayerLook), Interaction (PhysicsGrabber, Grabbable) and Puzzle (PuzzleTrigger, PressurePlate, SlidingDoor, PuzzleLight). Only PlayerInputReader reads the keyboard/mouse; the other Player and Interaction scripts use the IPlayerInput interface, so they don't depend on each other. Puzzle triggers and targets are linked by Inspector events, not code references. The class diagram and responsibilities are in Docs/Levo_class_diagram.png and Docs/ARCHITECTURE.md.
